# Startup and behavior audit — 2026-09-25

The reported clean-install behavior was hardcoded and misleading. `HarnessSettings` selected DeepSeek and a model without user configuration, and runtime model lists populated themselves from a static catalog. Consequently, deleting the application home still produced a “DeepSeek default / 3 models” row and missing-key errors. That row did not establish that an account, key, or model had been discovered.

This audit examined startup, provider configuration and removal, credentials, discovery, model selection, response parsing, tool execution, session recovery, and usage/status displays. It also preserved the earlier fixes for OpenAI-compatible token parameters and Responses routing. Changes are in source and require a rebuilt application.

Production bootstrap registers HTTP adapters. The reviewed request path consumes their streams; the tool runtime invokes tool implementations and reports execution, validation, and rendering failures as errors. I found no canned reply adapter substituted into those production paths. The repository's scripted adapters and fake servers are test fixtures. `sessions seed` is a separate, explicitly invoked synthetic load-test command, defaults to a temporary directory, and is not called at startup.

Session crash repair intentionally creates error records for missing tool outcomes and marks the turn interrupted. Those records say the tool's outcome is unknown. Session title fallback uses the first user prompt and records its source as `fallback`. These are recovery/display mechanisms, not evidence of successful model or tool execution.

The compatibility adapter still supports Chat Completions for providers that use it. GPT-5/GPT-6 model families on automatic routes, native OpenAI routes, and explicitly configured Responses routes use `/responses`. Both modern routing and legacy token-parameter negotiation have regression coverage; retaining the protocol adapter does not mean every model uses that protocol.

Verification used Windows, .NET SDK 10.0.401, and isolated build/data directories. The focused provider, discovery, routing, response, usage, and agent checks passed (308 tests). The final selection, patch, startup, ACP, and response checks also passed (29 tests). [StartupIntegrityTests](../tests/Blazorly.Harness.Tests/StartupIntegrityTests.cs) covers deletion/recreation, provider removal and restart, environment-only startup, malformed settings, and rendered Blazor pages. [ResponseIntegrityTests](../tests/Blazorly.Harness.Tests/ResponseIntegrityTests.cs) exercises interrupted HTTP response streams and proves they do not execute tool calls.

A separate running web application was checked over HTTP with a new `BLAZORLY_HOME`: `/api/llm.providers` returned zero configured providers, `/settings` rendered an empty provider table with no DeepSeek row, and `/` showed setup guidance. Merely launching/rendering did not create a settings file. The test process was stopped afterward.

The final broad suite completed with **751 passed and 42 failed (793 total)**. Unchanged commit `43da0cab2df46b76dfcadc782d174ec688fdfd13`, extracted and built separately, completed with **660 passed and the same 42 failures (702 total)**. Comparing failure names found no new failures. The remaining failures include `/bin/bash` assumptions on Windows, Linux sandbox/terminal and shell-hook expectations, CRLF-sensitive assertions, locked/read-only file cleanup, and tests that search for repository fixtures above an output directory placed outside the repository. These broader failures are not presented as passing checks.

Static catalog sizes/capabilities may still become stale, and a saved/discovered ID does not prove account access or successful inference. This audit used test provider servers rather than validating every external provider or third-party plugin. Deleting the harness home removes its stored settings, session data, and workspace registrations; it does not delete workspace folders elsewhere or browser-local appearance preferences.
