Settings tabs in Blazorly

The Settings page is five tabs along the top, a Save button, and a file on disk at ~/.blazorly/settings.json. Open it from the sidebar. Nothing here is a cloud console — the keys stay on this machine.

Blazorly Settings has five tabs: Appearance, Providers, Sessions & context, Capabilities, and Permissions & sandbox. Providers is where a new install starts: it sets the default provider and model for new sessions and lists every configured route — built-ins and custom gateways — with its API type, endpoint, models and key status. Sessions & context chooses JSONL or SQLite and the compaction window. Capabilities toggles tools (web, MCP, terminals, teams, System One, tool-gate). Permissions & sandbox sets the default preset for new sessions. Click Save. A live session can still switch model and permission from its own top bar without revisiting this page.

Providers

This tab is the default. The top picks the provider and model used for new sessions. Keys are stored per provider, so you can keep DeepSeek, Anthropic, and a local Ollama endpoint configured at once and pick among them from the session chip — a DeepSeek key is never sent to an OpenAI route. Local setups treat the key as optional.

Add a provider to open the setup dialog: pick a built-in or a custom gateway, choose the API type (OpenAI-compatible by default, Anthropic Messages where the endpoint speaks it), paste the key, then List models and tick the ones to keep — filter the list, Select all, or paste ids comma-separated. Saving adds a row to the table, where each route can be edited, rediscovered or removed. Use a custom gateway when the model is behind a proxy, a company gateway, or a local server that is not in the built-in catalog (include /v1 in the base URL for OpenAI-compatible gateways).

A custom name must be unique and must not collide with a built-in provider id. After Save, every row appears in the session model picker beside DeepSeek and the rest.

Sessions & context

  • Persistence — jsonl (one file per session) or sqlite (one database). Existing sessions stay where they were; blazorly sessions import migrates JSONL into SQLite.
  • Context window tokens — fallback only. If the provider catalog or API reports a window, that wins.
  • Max output tokens — clamped to the model’s own ceiling when known.
  • Compaction threshold — fraction of the window at which older turns get compacted. The log on disk is not rewritten; compaction is a surface projection.
  • Spill threshold — huge tool output is written to ~/.blazorly/spills instead of stuffing the prompt.
  • Telemetry — local aggregates of turns, tokens, and tool calls. Nothing leaves the machine.

At the top of this tab sits the default tool set: the same grouped picker as ⚙ Agent setup, but for every workspace at once. Turn a family off here and agents in all workspaces lose it — live chats included, once you Save — unless a workspace picked its own set in ⚙ Agent setup, which always wins. “Select all” stores no restriction at all, so tools added later (MCP servers, plugins) join automatically; anything less freezes exactly that list. The table below is the coarser layer: those switches unregister a capability from the app entirely and apply after a restart.

Permissions & sandbox

This tab sets the default for new sessions:

  • full-access — tools run on the host.
  • workspace-write — writes confined to the session folder. Linux Landlock jails bash and run_code.
  • read-only — mutations denied.

An already-open session does not jump when you Save here. Change that session from the lock chip on its header, or with /permission workspace-write. Optional: fail closed on macOS/Windows where Landlock does not exist, and an E2B remote sandbox if you want tools off this machine. E2B changes need a restart. More in permissions and sandbox.

Per-workspace agent setup

This Settings page is global. What the agent is in one project — its instructions and its tools — belongs to that workspace: open the workspace switcher in the sidebar and pick ⚙ Agent setup on the workspace row. Two tabs:

  • Instructions — the built-in instructions are shown; replace them completely with what this project needs. The built-in default is a full engineering charter: mission and accountability, requirements analysis, codebase discovery, planning, architecture, code quality, error handling, testing, security, performance, data integrity, APIs, dependencies, root-cause analysis, change management, documentation, autonomy, delivery standards, and response format. The identity header above it — the harness name, provider, model, and today’s date — always stays and is not editable. Placeholders {{provider}}, {{model}}, {{cwd}}, {{date}} and {{weekday}} are filled in per request; anything else stays literal. “Reset to default” restores the built-in text, and saving text you did not change stores no override at all.
  • Tools — which of the registered tools agents may use in this workspace, shown as capability families: files & code, run commands, background jobs, plans/tasks/goals, reminders, helpers & teammates, multi-step routines, web, past sessions, skills, ask-you-questions — plus one row per MCP add-on. A family switches its tools together, because they need each other (job_list without job_output is a half feature), and expands to individual tools when you want one of them off. Everything on means every tool, including ones added later (MCP servers, plugins); anything less freezes exactly that list, and disabled tools are hidden from the model and denied if it asks anyway.

The configuration is saved on the workspace (in workspaces.json, never in global settings), applies to every chat in that folder — including the subagents they spawn and blazorly run from that directory — and live chats pick it up on their next request. Project files (AGENTS.md / CLAUDE.md) still layer on top as runtime context; this is the instruction underneath them.

The built-in default is deliberately heavy: about 5,500 tokens, sent with every request of every agent in every workspace that has not replaced it. Small context windows feel it. A workspace that wants a lean prompt should replace the body with a few lines of its own — that is the cheapest trim available, since the fixed header above it (name, provider, model, today’s date) is a handful of tokens and is never editable.

What this page is not

Settings does not start a chat. It does not pick the workspace — that is the sidebar “New chat” menu. It does not switch Chat vs Trajectory — those tabs live on the session header. See session views and tabs.
